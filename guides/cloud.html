☁️ Cloud Security Architecture

Security design patterns, controls, and posture management across AWS, Azure, and GCP.

Cloud Changes the Architecture Problem

Cloud adoption shifts the security model in fundamental ways: the attack surface is elastic (grows and shrinks dynamically), the perimeter is API-defined (not physical), infrastructure is code (configuration is a security artifact), and the shared responsibility boundary creates accountability gaps if not understood clearly. Cloud security architecture is about designing controls that work with the cloud operating model, not against it.

Shared Responsibility Model

The single most important concept in cloud security. Every cloud provider operates on a shared responsibility model — they secure the cloud, you secure what you put in it.

Architect's Trap: The most common cloud security failure is misunderstanding responsibility boundaries. "The cloud provider handles security" is always partially wrong. You always own identity, data classification, and encryption key management.

Cloud Security Architecture Patterns

Multi-Account / Landing Zone Architecture

Enterprise cloud deployments should use separate accounts/subscriptions per environment and workload type. The AWS Organizations / Azure Management Groups model provides:

  • Blast radius containment — a compromised workload account cannot access security tooling accounts
  • Policy inheritance — Service Control Policies (SCPs) or Azure Policy enforce guardrails across the estate
  • Centralized logging — all CloudTrail/Activity Logs aggregated to a dedicated log archive account
  • Security tooling isolation — GuardDuty, Security Hub, Defender for Cloud operate from separate accounts

Hub-and-Spoke Network Architecture

The most common cloud network security pattern: a central "hub" VPC/VNet contains shared security services (firewall, SIEM ingestion, DNS), and "spoke" VPCs/VNets for individual workloads connect to the hub via peering or Transit Gateway. All egress traffic routes through the hub for inspection.

Defense in Depth — Cloud Layers

  • Edge — CDN WAF (CloudFront + WAF, Azure Front Door), DDoS protection
  • Network — Security Groups, NACLs, Network Firewall, NSGs, Azure Firewall
  • Compute — EDR agents, hardened AMIs, patch management, IMDSv2
  • Application — API Gateway, secrets management (Secrets Manager, Key Vault), SAST/DAST
  • Data — Encryption at rest (KMS, CMK), encryption in transit (TLS 1.2+), DLP, bucket policies
  • Identity — IAM least privilege, SCPs, Conditional Access, PIM

AWS Security Architecture

Core Services for Security Architects

  • IAM — roles, policies, SCPs; prefer roles over access keys; enforce MFA for console
  • Organizations + Control Tower — multi-account governance, landing zone automation
  • GuardDuty — threat detection (network, DNS, CloudTrail anomalies, S3, EKS, Lambda)
  • Security Hub — aggregates findings from GuardDuty, Inspector, Macie, Config, third-party tools
  • CloudTrail — API audit log; enable organization trail; log to separate account
  • Config — resource configuration tracking; managed rules for compliance; remediation actions
  • Macie — PII/sensitive data discovery in S3
  • Inspector — vulnerability scanning for EC2, ECR, Lambda
  • KMS — key management; prefer CMK (customer-managed keys) for sensitive workloads
  • VPC Flow Logs — network traffic analysis; critical for incident investigation

AWS Security Reference Architecture Key Patterns

  • Separate Security Tooling account from production accounts
  • Log Archive account with immutable S3 storage (Object Lock)
  • Management account used only for Organizations/billing — no workloads
  • SCPs to prevent disabling GuardDuty, CloudTrail, or Security Hub org-wide

Azure Security Architecture

Core Services for Security Architects

  • Entra ID (Azure AD) — identity foundation; Conditional Access; PIM for privileged roles
  • Defender for Cloud — CSPM + CWPP; Secure Score; regulatory compliance dashboard
  • Sentinel — cloud-native SIEM/SOAR; analytics rules; threat intelligence integration
  • Azure Policy + Management Groups — enforce guardrails across subscriptions at scale
  • Key Vault — secrets, keys, certificates; managed HSM for FIPS 140-2 Level 3 workloads
  • Monitor + Log Analytics — centralized logging; diagnostic settings for all resource types
  • Private Link + Service Endpoints — keep PaaS traffic off public internet

Cloud-Native Application Protection (CNAPP)

CNAPP unifies capabilities that were previously separate point tools into a single platform for cloud security posture across the full workload lifecycle:

ComponentWhat it does
CSPM (Cloud Security Posture Mgmt)Continuous misconfiguration detection across cloud resources; compliance mapping
CWPP (Cloud Workload Protection)Runtime protection for VMs, containers, serverless functions; vulnerability scanning
CIEM (Cloud Infrastructure Entitlement Mgmt)Identifies excessive permissions, orphaned identities, cross-account risk
KSPM (Kubernetes Security Posture)Misconfiguration detection for Kubernetes clusters, workloads, and RBAC
IaC SecurityScans Terraform/CloudFormation/ARM templates for misconfigurations before deployment

Leading CNAPP vendors: Wiz, Prisma Cloud (Palo Alto), Defender for Cloud (Microsoft), Lacework, Orca Security.

Identity in the Cloud — IAM Architecture Principles

  • Least privilege — grant minimum permissions required; review regularly with CIEM tools
  • No long-lived credentials — use roles/managed identities; rotate if keys are required
  • Workload identity — service accounts, managed identities, workload identity federation (no secrets in code)
  • Break-glass accounts — highly restricted, monitored emergency access accounts for each account/subscription
  • SCPs as guardrails — use Organization-level policies to prevent critical security controls from being disabled

Key Metrics for Cloud Security Posture

  • Mean Time to Remediate (MTTR) critical findings — target <24 hours for critical, <72 hours for high
  • Secure Score / Compliance % — benchmark across CIS, NIST, PCI baselines
  • Public exposure rate — % of storage buckets/databases with public access enabled
  • MFA coverage — % of human identities with phishing-resistant MFA
  • Encryption coverage — % of data stores encrypted with CMK

Role Prep: Be ready to design a cloud security architecture from scratch — a common interview exercise. Start with: shared responsibility clarification → account/subscription structure → identity model → network topology → logging strategy → threat detection → incident response. Working through this structure demonstrates architectural thinking, not just tool knowledge.
